# 结构化输出校验重试

## 这个知识点是什么

LLM 的文本输出不可靠,但程序需要可靠的数据。结构化输出就是让模型按 JSON Schema 产出,再用 Pydantic 校验成强类型对象。但"校验通过"不等于"符合业务约束"(比如"分数必须是 0-10 的数"这种 Schema 表达不了的规则),所以还需要**校验失败的闭环**:把校验错误文本回注给模型,让它修正后重试。

类比:让实习生填表。第一次填错不是骂一顿了事,而是把批注过的表递回去:"这里不对,照这个改"。递回次数有上限,超了就换人(抛异常走降级)。

## TradeWinds 为什么需要它

管道里四角色的每一次交接都是 Pydantic 模型:Planner 产出 `RetrievalPlan`、Analyst 产出评分列表、Editor 产出摘要。任何一处模型输出跑偏,下游就会拿到脏数据静默扩散。自研编排层不引入框架的"自动修复"魔法,所以把"校验-回注-重试"做成显式的两段:`OpenAICompatibleProvider` 的 `parse` 路径(schema 级校验)+ `StructuredRunner` 的业务级校验重试。

## 本项目怎么实现的

两层配合,见 [agents/orchestrator/structured.py](../../src/tradewinds/agents/orchestrator/structured.py):

- **schema 级**:`OpenAICompatibleProvider.complete(response_model=...)` 走 OpenAI SDK 的 `beta.chat.completions.parse`,由供应商按 JSON Schema 约束生成并解析成 Pydantic 实例,`LLMResult.content` 已是模型对象;
- **业务级**:`StructuredRunner.run(prompt, response_model, model)` 拿到结果后仍有 `isinstance` 检查和 `model_validate` 兜底(防供应商未走 parse 路径),`ValidationError` 被序列化成一句反馈消息追加到对话(`"你的输出不符合 schema……错误:..."`),重试上限 2 次,耗尽抛 `LLMError` 进统一异常通道。

为什么不在 schema 里写死所有规则?JSON Schema 表达不了跨字段/业务规则,而且规则全塞 schema 会挤占模型注意力——把业务校验留在 Python 里、错误文本回注,是可靠性和 prompt 可读性的平衡。

## 踩过的坑

1. **`parse` 路径不能假设一定返回模型实例**:部分兼容供应商会降级成普通 JSON 字符串,所以 `StructuredRunner` 保留了 `model_validate` 兜底分支,类型检查(`isinstance`)放在最前;
2. **重试的"上限 2 次"是重试次数,不是总调用次数**:总次数 = 1 + 2 = 3,测试断言时容易写错(本项目就在断言里注释了这一点);
3. **校验错误的 `str(exc)` 很长**,包含全部字段路径与输入值——回注时可直接用,但落日志时要注意别把用户原文带进日志(AGENTS.md 的敏感信息纪律)。
