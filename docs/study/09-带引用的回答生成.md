# 带引用的回答生成

## 这个知识点是什么

带引用(citation)的回答,是让 LLM 在陈述事实的地方标注"这条信息来自哪",并给用户可点击的原文链接。它不是简单的 RAG 拼接——核心是**编号契约**:模型在正文里写 `[1]`,程序保证编号 1 确实指向某个真实 URL,并把这种对应关系持久化、随回答一起交付。

类比:学术论文的参考文献——正文上标的 [1],一定能在文末列表里找到对应条目;审稿人(用户)点开就能核对原话。

## TradeWinds 为什么需要它

对话研究 Agent 的价值在"可信":用户问一个研究问题,Agent 检索多源后综合作答。没有引用,回答和普通聊天机器人没差别,用户无法核验;引用让每一条事实可溯源——这也是 design.md 把"结论带编号引用"列为 M4 里程碑验收标准的原因。

## 本项目怎么实现的

三层配合:

- **prompt 约定**([agents/prompts/chat.md](../../src/tradewinds/agents/prompts/chat.md)):要求模型"句末用 [编号] 标注引用,编号对应你实际检索到的来源 URL;没有来源支撑的论断不许加编号"——先用规则约束模型行为;
- **引用提取**([services/chat_service.py](../../src/tradewinds/services/chat_service.py) 的 `extract_citations`):按序扫描工具轨迹的返回文本,用正则提取 URL,去重后编号 1、2、3…… 这一步是**程序而非模型**在建立"编号→URL"的映射,所以编号与 URL 的对应关系永远可靠——模型只负责"用编号",程序负责"编号是什么";
- **持久化与交付**:引用列表(JSONB)与工具轨迹一起存进 assistant 消息,支持历史会话回看;SSE 流里 `citations` 事件先于正文 delta 发出,前端可先渲染引用列表。

设计取舍:不做"模型输出引用再逐条验证 URL 是否真的支撑论断"的强校验(成本高),而是保证**引用列表里的 URL 全部真实出现在工具检索结果中**——引用可以少,但不会假。

## 踩过的坑

1. **URL 边界截断**:工具返回文本里 URL 后常跟标点或括号(`https://a.com/x。`),正则要用终止字符集 `[\s)"'>\]]`,并 `rstrip(".,;")`,否则引用链接带尾巴、点击 404;
2. **编号对不上**:若让模型自己维护"文末参考文献列表",编号和正文标注经常错位。把映射完全交给程序按出现顺序生成后,该问题消失——**模型负责标注位置,程序负责映射**;
3. **同一 URL 多次出现**:工具结果间重复链接要全局去重(而非每条轨迹内去重),否则引用编号会"跳号"。
