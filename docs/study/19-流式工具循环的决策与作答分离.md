# 流式工具循环:决策与作答分离

## 这个知识点是什么

让 Agent 的最终回答"逐字流到用户眼前",难点不在流式本身——LLM SDK 的 `stream=True` 人人会用——而在**工具循环里你不知道这一轮是不是最后一轮**。如果每轮都用结构化输出(要求模型把回答装进 JSON 的 `content` 字段),那么即使第 N 轮模型给的是答案,它也是"一次性生成完"的完整 JSON:流式通道拿到的是已经生成完的文本,只能切片假装流式。

解法是把"决定做什么"和"生成回答"拆成两种调用:**决策轮**只输出一个小 JSON(`{"tool_calls": [...]}`,空数组=信息够了),**作答轮**在决策为"可以作答"后才发起,走纯文本流式。决策轮输出短、成本低;作答轮没有 JSON 包裹,每个 token 生成即下发。类比:先让助理写张便签"我去查资料了/查完了",便签不需要好看;真正写报告时才打开文档边写边给你看。

## TradeWinds 为什么需要它

MVP 的对话是"伪流式":`chat_service` 等整个工具循环跑完、拿到完整回答,再 `chunk_text` 切成 80 字符的 delta 下发——用户要等 LLM 把全部答案生成完才看到第一个字,与"流式研究助手"的产品承诺(G1、§6 流式输出)不符。根因正是上面的结构:决策与作答共用一个结构化 schema(`AssistantTurn`),答案被囚禁在 JSON 字符串里。拆开之后,引用列表还能提前确定(它来自工具轨迹,作答前已完整),SSE 事件序 `citations → delta* → done` 得以原样保留,前端零改动。

## 本项目怎么实现的

- **决策 schema**(`loop.py`):`LoopDecision(tool_calls: list[ToolCallRequest] = [])` 取代原 `AssistantTurn`——只保留"要调什么工具"一个字段,空列表即"请求作答"。schema 本身就是协议:strict JSON schema 强制模型在"调工具"和"不调"之间二选一,不靠 prompt 自觉;
- **作答轮**(`ToolLoop._run_inner_streaming`):决策为空后,循环在消息尾部追加一条作答指令(`_ANSWER_INSTRUCTION`),调用 `provider.stream()` 逐 token 转成 `AnswerDeltaEvent` 透出;
- **事件契约**:`run_streaming() -> AsyncIterator[LoopEvent]`,事件序固定为 `ToolTraceEvent*(每次工具执行) → AnswerDeltaEvent*(作答增量) → LoopDoneEvent(含聚合 usage 与 stopped_reason)`;非流式的 `run()` 退化为消费同一事件流取结果,一套实现两条入口;
- **流式契约演进**(`llm.py`):`stream()` 从 `AsyncIterator[str]` 改为 `AsyncIterator[StreamEvent(delta, usage|None)]`——作答轮的 token 计量靠最后一个事件携带 usage(OpenAI 的 `stream_options.include_usage`);供应商不认这个参数时降级重试一次,代价是该次 usage 记 0;
- **半截回答不丢**:`_LoopState` 跨事件累积答案与工具轨迹,超时(`stopped_reason="timeout"`)和流中断(`"stream_interrupted"`)时,已产生的增量以部分内容收尾,而不是回退成空串;
- **SSE 转发**(`chat_service._stream_and_persist`):循环跑在独立任务里,事件经 `asyncio.Queue` 转给 SSE 生成器;首个 delta 发出前 flush citations 事件。客户端断连只取消 SSE 生成器,任务继续完成落库与计量(study 08 的断连语义不变)。循环抛 `LLMError` 时转成 SSE `error` 事件,不再静默断流;
- **引用校验**(`verify_citations`):回答完成后剔除越界 `[n]` 标记,持久化只保留实际被引用的条目。直播 citations 事件仍发全量来源列表——作答开始前无法预知模型会引用哪些编号,直播视图=来源列表、刷新后=实际引用,是有意的取舍。已知边界:编号合法但内容无中生有的引用无法在代码层检测,仍靠 prompt 约束。

## 踩过的坑

1. **ContextVar 不会传给已创建的任务**:`set_rag_user` 原先在 `create_task` 之后才执行,而任务在创建瞬间就复制了 context——后台任务里的 RAG 历史检索始终拿不到用户标识(潜在 bug,本次重构顺手修正:置入移到 `create_task` 之前);
2. **usage 不在 chunk 里而在"空 choices 的收尾块"里**:开启 `include_usage` 后,最后一个 chunk `choices=[]`、只带 usage,按 `chunk.choices[0]` 取增量会在收尾块上炸 IndexError;
3. **测试里 pydantic 模型不支持位置参数**:`Usage(1, 1, 2)` 直接 TypeError,必须关键字传参——写假件时习惯性用了 dataclass 的写法;
4. **超时保内容的测试要控制增量到达时机**:FakeProvider 若在每个 delta 前都 sleep,超时触发时一个增量都没到,测不到"部分内容保留"——让首个 delta 立即到达、在第二个 delta 前停顿,才能命中超时窗口。
