# TradeWinds 扩展计划

| | |
|---|---|
| 版本 | v0.1 |
| 日期 | 2026-09-06 |
| 状态 | 评审中 |
| 关联文档 | [设计文档](design.md) |

> 本文档描述 TradeWinds 从单实例 MVP 到多用户规模化运营的演进路线。原则：**由指标触发演进，不为想象中的规模提前买单**。每个阶段列出触发信号——达到信号才启动下一阶段改造。

## 1. 容量基线（阶段 0 的天花板估算）

单 VPS（4C8G）+ Docker Compose 的合理承载量级：

| 维度 | 估算 | 瓶颈来源 |
|---|---|---|
| 注册用户 | 1 万以内 | DB 单实例写压力、Worker 吞吐 |
| 活跃主题 | 3-5 万个 | 队列任务量 = 主题数 × 频率 |
| 对话并发 | 数十路 SSE | 单进程异步 IO 可支撑，瓶颈在 LLM 上游限流 |
| LLM 成本 | 与活跃主题数线性相关 | 阶段 0 最大的成本变量，需先于架构到达天花板 |

结论：**阶段 0 的真实瓶颈更可能是 LLM 成本与上游限流，而非服务器架构**——因此成本治理贯穿所有阶段。

## 2. 演进阶段

### 阶段 0：单实例 MVP（上线起点）

架构即设计文档所述：单 VPS，api / worker / beat / postgres / redis / caddy 六容器。

**必做**（上线即有，不因规模小而省略）：

- 每日数据库备份（pg_dump 异地存储），并演练过一次恢复
- 队列长度、任务失败率、LLM 成本三个核心指标的监控与告警
- Sentry 错误上报、结构化日志

### 阶段 1：分离与加固（约 1k-1w 注册用户）

**触发信号**：DB CPU 持续 > 60%，或 Worker 任务积压常态化（队列长度持续增长），或单 VPS 内存吃紧。

改造内容：

1. **数据库独立实例**：PostgreSQL 迁出应用 VPS（云托管 RDS 或独立机器），启用连接池（pgbouncer）
2. **Worker 水平扩展**：worker 容器无状态化验证通过后，同机多副本起步，跨机扩展随时可行
3. **静态资源上 CDN**：前端构建产物走 CDN，回源到对象存储
4. **可观测升级**：指标从日志抽取升级为 Prometheus + Grafana，补全请求延迟分位数、SSE 连接数等业务指标
5. **LLM 网关雏形**：统一入口层接管计量、限流与供应商切换，为多供应商路由做准备

### 阶段 2：多应用实例（约 1w-10w 注册用户）

**触发信号**：单 api 容器无法承载峰值流量，或需要滚动更新零停机。

改造内容：

1. **API 无状态化 + 多实例**：确认会话与状态全部外置（JWT 无状态 + DB/Redis），负载均衡（Caddy 升级为 Nginx/云 LB）挂多个 api 实例，滚动发布
2. **调度器单点治理**：Beat 保证全局仅一个实例运行（分布式锁），任务按类型路由到不同队列（检索重任务 / 推送轻任务分离）
3. **SSE 广播化**：对话流式输出经 Redis pub/sub 中转，实例无关，任意实例可服务任意会话
4. **读写分离**：只读副本承接 Feed/报告等读多写少查询
5. **数据治理**：items 原始内容归档策略（热/冷分离）、按时间分区，raw_content 迁移到对象存储
6. **成本工程**：LLM 结果缓存命中率优化、低峰错峰调度（用户时区感知）、供应商比价路由

### 阶段 3：平台化（10w+，或商业化后）

仅在商业模式验证后启动，此处只留路标：

- 容器编排升级（K8s 或云容器服务），多可用区
- 队列优先级体系：付费用户任务优先、对话任务实时级、批任务低优先级
- 多供应商 LLM 容灾与降级矩阵（主供应商故障自动切换）
- 数据仓库与用户行为分析（留存、主题健康度）
- 合规升级：隐私政策、数据导出与注销、审计日志

## 3. Agent 能力演进路线（与规模无关，按产品价值排序）

| 能力 | 说明 | 依赖 |
|---|---|---|
| 跨会话记忆 | 用户关注历史影响打分与推荐，越用越准 | items 评分历史 → 用户偏好画像 |
| 周期报告 | 日报/周报聚合与分享页（一期 M5 后第一个迭代） | 现有管道聚合 |
| 主动推送完善 | 阈值动态化（按主题冷启动表现自适应）、站内通知渠道 | push_log 数据积累 |
| 自定义 RSS 源 | 用户提交源，进入 Planner 源选择范围 | 源健康度校验机制 |
| RAG 检索用户已读内容 | "我上周看过的那篇讲 xx 的文章" | 向量库（PostgreSQL pgvector 优先，不引入独立向量库） |
| 评测体系常态化 | 金标集扩充 + 线上抽样人工标注 + prompt 变更回归门禁 | 评测基础设施 |

原则：**Agent 能力演进与基础设施演进解耦**——前者靠评测门禁保质量，后者靠指标触发保稳定。

## 4. 风险随规模的演变

| 风险 | 阶段 0 | 阶段 1+ |
|---|---|---|
| LLM 成本 | 配额硬限即可 | 网关统一治理 + 每用户配额分层（免费/付费） |
| 单点故障 | 接受（快速恢复优先） | DB/Redis 高可用，api 多实例 |
| 数据丢失 | 每日备份 | 备份 + WAL 归档，RTO/RPO 明确化 |
| 上游限流 | 单供应商重试 | 多供应商路由 + 全局并发预算 |
| 运维复杂度 | Compose 一把梭 | 明确的 runbook：扩容、回滚、灾备演练脚本化 |

## 5. 明确不做的扩展（持续否决）

- 自建 LLM 推理（除非成本曲线证明自建 GPU 合算，短期不可能）
- 自建搜索引擎（沿用"公开 API + 通用抓取"边界）
- 微服务拆分（单体多进程架构在 10w 用户前不构成瓶颈，拆分只增加复杂度）
