## 1. 背景与定位

信息获取存在两类真实痛点：

1. **主动检索成本高**：想了解"最近 Agent 领域有什么新进展"，需要跨 arXiv、Hacker News、GitHub、技术博客等多个来源反复搜索、筛选、阅读，一次认真的调研耗时 1-2 小时。
2. **被动订阅不精准**：RSS/Newsletter 是"源级订阅"而非"主题级订阅"——订阅一个源会收到大量无关内容，而真正关心的细分主题（如"具身智能的抓取策略"）没有对应的信息源。

**TradeWinds（信风）** 是一个「AI 信息研究助理」：

- **对话咨询**：用户像和研究员聊天一样提问，Agent 多步检索、交叉验证，带原文引用地回答；
- **主题订阅**：用户用自然语言创建监控主题，Agent 持续跟踪，产出带原文链接、摘要与推荐理由的条目流（Feed）；
- **周期报告**：按周期将条目聚合成结构化日报/周报，存档可分享；
- **主动推送**：高价值条目（超阈值评分）即时推送，不等周期报告。

一句话定位：**把自然语言描述的兴趣，变成持续、精准、带来源的信息流。**

slogan：把风声，吹给你。

目标用户画像：有持续信息追踪需求的开发者、研究者、行业分析师。产品面向**多用户公开运营**，注册即用。

## 2. 目标与非目标

### 2.1 目标

- G1：对话式研究 Agent，回答中每条关键结论均带可点击的原文引用
- G2：主题订阅全流程可用：创建 → 定时检索 → Feed 呈现 → 邮件推送
- G3：核心链路有降级与重试，单信息源故障不影响整体出报；核心服务可用性满足真实运营要求
- G4：LLM 成本可估算、可控制（分级模型 + 缓存 + 配额），每用户成本可计量
- G5：可真实运营：注册/登录、配额限制、公网可访问、可观测（日志/健康检查/错误上报）
- G6：架构为多用户规模预留演进空间，扩展路径见 [扩展计划](scaling-plan.md)

### 2.2 非目标（明确不做）

- N1：实时流式监控（新内容秒级推送）——周期任务 + 阈值推送已满足需求
- N2：全文托管与版权内容再分发——只存摘要与链接，指向原文
- N3：移动端 App——Web 优先，邮件作为主要触达渠道
- N4：团队协作、多角色权限——单用户视角
- N5：自建搜索引擎或通用爬虫框架——使用各来源的公开 API 与通用网页抓取

## 3. 用户旅程

### 3.1 订阅用户（主路径）

1. 注册登录，创建主题："近一周的 Agent 新技术"，设置频率（每天/每周）
2. 系统将主题编译为检索计划；到达执行时间后，后台 Agent 检索多源、过滤、摘要
3. 用户在 Feed 页看到条目：**原文链接 + 标题 + 摘要 + 推荐理由 + 相关度评分**，点击进入原文
4. 周期结束生成报告（日报/周报），推送至邮箱
5. 评分超过阈值的条目即时邮件推送（带抑制策略，避免打扰）

### 3.2 咨询用户

1. 在对话页提问："Agent 框架最近有什么值得看的新东西？"
2. Agent 拆解问题 → 调用检索工具 → 抓取原文 → 综合回答，流式输出，结论附引用
3. 用户可追问、可要求深挖某个条目

### 4.1 Agent 编排层（自研）

不引入 LangGraph/PydanticAI 等编排框架，自研轻量编排层，底层使用 OpenAI-compatible SDK（DeepSeek/GLM 等均兼容该协议）。

**选择自研的理由**：本项目的 Agent 形态不需要图编排能力；自研几百行且测试覆盖，比黑盒依赖更可控；编排机制（工具循环、结构化输出、流式）本身是项目要展示的核心能力。

**编排层职责**（且仅承担以下职责，不含业务逻辑）：

- 工具循环执行器：维护消息上下文，执行模型发起的工具调用，将结果回注对话
- 结构化输出：Pydantic 模型定义 + 校验失败自动重试
- 流式输出：SSE 转发，处理客户端断连
- 容错：指数退避重试、超时控制、上下文超长截断
- 计量：token 用量与成本统计，按用户/角色维度上报

**已知风险与对策**（自研最容易翻车的三处，实现时必须显式设计并测试覆盖）：

1. 上下文超长：截断策略优先保留系统指令与最近工具结果
2. 工具调用失败：失败信息作为工具结果回注，让模型自行调整，而非中断循环
3. SSE 中断：客户端重连后可从消息历史恢复，不重复计费已生成的部分

**四角色分工**：

| 角色 | 输入 | 输出 | 模型档位 | 触发方式 |
|---|---|---|---|---|
| Planner | 主题自然语言描述 | 检索计划（关键词组、源选择、时间窗、判定标准） | 低 | 主题创建/编辑时 |
| Retriever | 检索计划 或 对话问题 | 候选条目集合（含原文内容） | 低 | 定时任务 / 对话请求 |
| Analyst | 候选条目 + 主题描述 | 评分、去重聚类、过滤 | 低 | 检索完成后 |
| Editor | 通过过滤的条目 | 单条摘要+推荐理由；周期报告 | 中 | 打分完成后 / 报告任务 |

设计原则：

- **对话与订阅共用 Planner/Retriever/Analyst**：对话即"一次性主题"，订阅即"持久化主题"，核心管道同一套
- **多 Agent 的价值在分工而非表演**：每个角色职责单一、prompt 独立、可单独评测与替换模型档位
- **角色间传递的数据全部为经过校验的结构化数据**

### 4.2 关键流程

**主题编译（Planner）**

输入："近一周的 Agent 新技术"，输出结构化检索计划：关键词组合、适配的信息源（arXiv 分类 / HN / GitHub / Web 搜索）、时间窗、相关性判定标准。计划在创建时返回预览，用户可修正关键词。

**订阅执行（异步任务）**

1. Beat 到期将主题执行任务入队，Worker 消费
2. Retriever 按计划并发抓取各源（httpx 异步），基于已见 URL 指纹做增量
3. Analyst 打分与聚类；单源失败时跳过该源并标注降级，不阻塞整体
4. Editor 为通过条目生成摘要与推荐理由
5. 条目入库；超阈值条目进入即时推送任务；累计条目等待周期报告

**对话研究（同步，SSE）**

1. 用户消息进入 Retriever 工具循环：拆解 → 检索 → 按需抓取原文 → 评估充分性
2. 循环上限：单轮工具调用次数与总时长双限制，超限则基于已有信息作答并声明局限
3. Editor 汇总生成带引用的回答，SSE 流式返回；引用编号对应原文链接

## 5. 数据模型（概要）

核心实体与关系：

- **User**：注册用户，持有配额与通知偏好
- **Topic**（订阅主题）：属于 User，含自然语言描述与 Planner 编译产物，带执行频率与调度状态
- **Item**（信息条目）：属于 Topic，来自单一信息源，含原文链接、摘要、评分与聚类标识，全生命周期有状态流转
- **Report**（周期报告）：属于 Topic，聚合某周期的条目
- **Conversation / Message**：对话会话与消息，消息持久化引用与工具轨迹
- **PushLog**：推送记录，支持去重与审计

设计约束仅三条：所有实体归属清晰支持多租户隔离；条目需支持"主题内 URL 去重"与"跨周期聚类"；调度状态需支持按到期时间批量扫描。具体字段、索引与约束在实现阶段通过迁移工具（Alembic）设计与演进。

## 6. API 设计（v1，前缀 `/api/v1`）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | /auth/register, /auth/login | 注册；登录签发令牌 |
| GET/POST | /topics | 主题列表 / 创建（创建时同步返回检索计划预览） |
| PATCH/DELETE | /topics/{id} | 编辑（重新编译计划）/ 删除 |
| POST | /topics/{id}/run | 手动触发一次执行（受配额限制） |
| GET | /topics/{id}/items | Feed 分页；支持增量与评分过滤参数 |
| GET | /topics/{id}/reports, /reports/{id} | 报告列表 / 详情（支持公开分享 token） |
| POST | /conversations | 创建会话 |
| POST | /conversations/{id}/messages | 发送消息，SSE 流式返回 |
| GET | /healthz, /readyz | 存活 / 就绪（依赖连通） |

认证采用 JWT；登录/注册按 IP 限流（Redis），主题执行按用户配额。接口契约以 OpenAPI 文档为准。

## 7. 推送策略

- **即时推送**：条目评分超过阈值（10 分制 8 分，配置项 `TRADEWINDS_PUSH_IMMEDIATE_THRESHOLD`）→ 立即邮件；同一聚类 24 小时内只推送一次（窗口 `TRADEWINDS_PUSH_CLUSTER_SUPPRESS_HOURS`）
- **周期推送**：频率到期时聚合生成报告并邮件推送；周期内无有效条目发送轻量汇总（可关闭）
- **抑制规则**：同一聚类的条目在 24 小时内只推送一次；具体去重键在实现阶段设计
- 邮件发送失败重试（指数退避），仍失败记录并可查询；所有外发邮件带退订链接

## 8. 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 语言/框架 | Python 3.13 + FastAPI | 异步友好，类型标注配合 Pydantic 贯穿全链路 |
| 数据库 | PostgreSQL 16 + SQLAlchemy 2.0 (async) + Alembic | 关系型主存储，JSONB 承载灵活结构 |
| 缓存/中间件 | Redis | 任务队列 broker、限流计数、热点缓存、SSE 广播备用 |
| 任务队列 | Celery（Worker 与 Beat 独立容器） | 成熟的生产级队列：重试、路由、并发控制、监控生态齐全 |
| Agent 编排 | 自研轻量编排层（见 4.1）+ OpenAI-compatible SDK | 核心能力自持，依赖最小化 |
| LLM | DeepSeek 为主，双档位（打分/检索用低价位，摘要/对话用中档），Provider 抽象可切换 | 成本可控；协议统一，替换供应商只改配置 |
| Web 搜索 | Tavily 或 Brave Search API | 对话研究需要通用检索；实现期实测免费额度后定 |
| 前端 | React SPA（Vite + TypeScript），SSE 消费流式响应 | 多用户运营产品，交互体验优先 |
| 邮件 | 专业发信服务（Resend 或同类） | 送达率与可维护性优于自建 SMTP |
| 部署 | Docker Compose（api / worker / beat / postgres / redis / caddy），Caddy 自动 HTTPS | 单 VPS 起步，容器边界清晰，向多机演进平滑 |
| CI/CD | GitHub Actions：lint + test → build image → 部署 | 推送即上线 |
| 可观测 | structlog 结构化日志 + Sentry + 健康检查 + LLM 成本报表 | 生产基本盘 |

## 9. 测试策略

- **单元测试**：评分过滤、URL 去重、推送抑制、配额与计量等纯逻辑，覆盖边界
- **契约测试**：各信息源客户端对录制响应的解析正确性
- **编排层测试**：工具循环（含工具失败回注）、结构化输出重试、流式中断恢复——自研部分的测试是一等公民
- **Agent 评测**：固定"金标集"（若干主题 + 期望检索计划要点），Planner 输出比对；Retriever/Editor 用离线样例数据跑管道断言产物结构；金标集随迭代扩充，防止 prompt 改动引入回归
- **集成测试**：真实 Postgres/Redis 容器，覆盖 注册 → 建主题 → mock 源抓取 → 出条目 → 推送 全链路
- LLM 调用在测试中一律 mock，保证 CI 稳定与零成本

## 10. 里程碑（一期 MVP）

- M1：项目骨架、配置管理、DB 迁移、注册登录、Redis 接入、健康检查（可部署空壳上线）
- M2：自研编排层 + 四角色管道，手动触发跑通检索→打分→摘要（核心能力）
- M3：Feed API + Celery 定时执行 + 邮件推送（订阅闭环）
- M4：对话研究 Agent（工具循环 + SSE + 引用）
- M5：React 前端三个界面（订阅/Feed/对话）、限流配额、CI/CD、监控，正式上线

二期方向：周期报告与分享页、主动推送完善、跨会话记忆、自定义 RSS 源；规模演进见 [扩展计划](scaling-plan.md)。

## 11. 风险与对策

| 风险 | 对策 |
|---|---|
| LLM 成本失控 | 分级模型 + 打分前内容截断 + 每用户成本计量与报表 + 配额硬限 |
| 信息源 API 变更/限流 | 客户端层隔离，单源降级不影响整体；遵守速率限制并本地缓存 |
| Planner 编译质量不稳定 | 金标集评测 + 用户创建时预览并修正计划 |
| 自研编排层缺陷 | 职责边界收敛（4.1）、三处已知风险显式设计与测试、必要时可替换为轻框架兜底 |
| 队列任务堆积 | Worker 并发可调 + 任务超时 + 队列长度监控告警 |
| 邮件进垃圾箱 | 独立发信域名 + SPF/DKIM/DMARC + 退订链接 |
| 版权风险 | 只存摘要与链接，摘要标注来源，提供原文跳转 |

## 12. 已定决策与遗留问题

已定：Agent 编排自研；前端 React SPA；LLM 以 DeepSeek 为主、Provider 可切换。

遗留（实现期定）：

1. Web 搜索 API 选型（Tavily vs Brave，实测免费额度）
2. 邮件发信服务商（Resend vs 同类，看价格与送达率）
3. 域名与品牌资产注册
