## 目标

一次性完成扩展计划中剩余的全部纯代码项,继续按"细分提交 + 详细正文 + 逐步推送"执行,全部不依赖上线环境(真实 LLM/嵌入调用一律 mock,集成测试由 CI 真库验证)。

## 迭代 A:评测体系常态化(test(agents))

1. `tests/agents/golden/analyst_cases.json`(≥8 例):给判定标准 + 候选条目(标题/正文)+ 录制模型输出,断言业务要点——高相关条目 ≥7 分、营销噪音 ≤3 分、同一事件的多条记录共享 cluster_key、每条输入都出现在输出中。
2. `tests/agents/golden/editor_cases.json`(≥6 例):给条目 + 录制摘要,断言结构要点——summary 含条目核心实体、长度下限、reason 非空(不逐字比对)。
3. 新增 `tests/agents/test_analyst_editor_golden.py`:与 Planner 金标同一套模式(录制固件 + 期望断言,CI 必跑),另含规模守卫(各金标集最少条数,防静默清空)。
4. 至此三角色均有金标集,prompt 文件变更 = 金标测试必须过 = 回归门禁;在测试 docstring 与计划文档写明该机制。

## 迭代 B:推送阈值动态化(feat(push))

1. 纯函数 `effective_immediate_threshold(recent_scores, global_threshold, *, min_history=10, adjust=1.0) -> float`:
   - 历史不足 min_history(冷启动)→ 全局阈值;
   - 否则取最近 accepted 条目评分中位数,自适应到 `[global-1.0, global+1.0]` 区间——高分主题抬高门槛避免刷屏,低分主题轻微下调浮出精华。
2. `PipelineService.run_topic` 每次执行时查询该主题最近 20 条 accepted 评分(排除本次新条目),计算有效阈值用于即时推送判定;`_immediate_threshold` 参数保留为全局兜底。
3. Settings 不新增项(min_history/adjust 为常量,避免过度配置);单元测试覆盖冷启动/抬高/压低/clamp 四个分支;集成测试:种子高分历史 → run → 立即推送被自适应门槛抑制。

## 迭代 C:RAG 已读内容检索(feat(rag),pgvector 方案)

1. **迁移 0010**:`CREATE EXTENSION IF NOT EXISTS vector` + `item_embeddings` 表(item_id 主键/级联 FK、`embedding vector` 不锁定维度——MVP 精确检索无需 ivfflat,模型换维度不用迁移,注明升级路径)、model、created_at。
2. **镜像切换**:docker-compose 与 CI 的 postgres 换为 `pgvector/pgvector:pg16`(纯配置)。
3. **嵌入客户端** `agents/orchestrator/embeddings.py`:OpenAI-compatible `/embeddings` 调用,Settings 新增 `TRADEWINDS_EMBEDDING_MODEL`(None = 功能关闭,默认关);错误包装复用 LLMError。
4. **管道生成**:PipelineService 增可选 `embedder` 注入点,accepted 条目定稿后对 `title + summary` 生成嵌入并 upsert 入 `item_embeddings`;失败记 warning 不阻塞管道(降级原则)。
5. **检索**:`services/rag_service.py` `search_user_items(session, embedder, user_id, query, limit)`——查询向量化后对用户自己的条目做 cosine 距离 top-K;REST `GET /api/v1/items/search?q=`(鉴权,仅本人条目);对话工具 `search_history` 挂入 build_chat_registry(回答"我上周看过的那篇讲 xx 的文章"类问题),用短会话解耦(模式同 SessionUsageRecorder)。
6. **测试**:嵌入客户端单元测试(mock SDK);集成测试用假 embedder(定长向量)验证 run → embedding 落库、检索端点返回本人条目且按相似度排序、跨用户隔离。
